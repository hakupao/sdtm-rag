## 保留下来的做法
- **把 workflow 里的 shell 编排搬进有单测的 Python。** workflow 的 job 只在 main 上执行, 分支上验不了; 逻辑留在 YAML 里就只能靠读。搬进 `kbsync.py deploy-public` 之后, 每条失败路径都能用带容器状态的假 docker 跑, 并在「换数据 / 退数据的那一刻正式容器必须是停的」这类时刻核对不变量。workflow 只剩三行接线。
- **不变量由替身自己记账, 不靠 raise。** 编排在动过正式容器之后会接住所有异常并停机, 假 docker 里 raise 的断言会被吞掉。改成往 `violations` 里记、测试末尾统一检查。
- **`if` 条件做成真值表, 表本身是测试数据。** 另有一条测试保证「新加一个带 `if` 的步骤而表里没有」会变红; 文档里的表由同一份数据生成。
- **能用真实工具只读核对的就核对。** 生成的临时验收 compose 文件喂给部署机上的 `docker compose config` 校验 (不创建任何东西); 两段 key 探测脚本在本机用真实 key 和无效 key 各跑一次。假实现证明不了的, 这两步补了一部分。
- **写状态机之前先问。** 「原本停止 + 验收通过」怎么办, 三种做法对应三种状态机; 做完第一项就停下来问, 答案回来再写, 没有返工。

- **每一轮修正都再送审, 而不是自己说「已改」。** 第一轮意见的修正送了增量审查, 结果审出我在修正里新引入的一个问题 (统一的异常处理把「动过正式容器之后」的个别错误报成「没有动」); 第二轮的修正和后来的补充裁定又送了第三轮, 审查者把对方分支上的真脚本拿出来跑, 指出我的测试替身有 5 处与它不一致。任务书里明确写「处置一列是写作者的说法, 不要采信」。

- **改正在用的东西时, 用「改前改后各执行一遍、逐项对照」来证明没变。** 私有部署 job 的标签步骤, 测试里把基点的脚本和现在的脚本都交给真实 bash 执行, 比较退出码、写进 `GITHUB_OUTPUT` 的各行和打印的内容; 再加一条测试对照基点, 断言整个 job 只有预期的 4 个步骤不同、脚本的差别只是把内联表达式换成变量。「只做加固」因此是可以机械核对的, 不是一句保证。

## 必须补上的缺口
- **变异清单是写的人自己列的, 列不到的地方就是盲区。** 第一轮 62 条里漏了整段 `ANSWER_KEY_PY` (假 docker 只按脚本文本匹配、返回预设结果, 脚本内部一行都没执行), 是代码审查指出来的。对策: 凡是「字符串形式、在别处执行」的代码 (容器里跑的脚本、shell 片段), 单独列一栏, 确认每一段都有执行到它的测试。
- **测试数据没有分辨力又撞上一次 (规则 6 成因 D)。** 越界目录名的测试用了一个不存在的路径, 去掉名字校验后「目录不存在」照样拦下它。变异才查出来。对策已用在本轮: 反例数据要让「另一道防线」失效, 只留被测的那一道。
- **「状态读一次用到底」的问题两位审查者里只有安全审查看出来。** `prev_running` 在几分钟的临时验收之前读取, 期间被人工停下的站点会被重新拉起。自己写的场景测试全是「状态不变」的世界。对策: 状态机里每个「读状态」与「按状态动手」之间隔着耗时步骤的地方, 加一条「中间被改了」的场景。
- **用户输入的格式校验照搬了旧写法。** `grep -Eqx` 是逐行匹配, 我新写的步骤也跟着用了; 安全审查实测出多行输入可绕过。继承代码里的同款问题这次没有动 (不在范围内), 已上报。
- **修正本身会引入问题, 而且越到后面越容易被当成「小改动」放过。** 三轮审查里有两轮的最重一条都出在上一轮的修正上。最后一轮意见的修正没有再送审 (收尾时如实写了)。对策: 修正和原始实现同等对待 —— 同样补测试、同样做变异、同样写进「未经独立审查」的清单, 直到有人审过。
- **替身照着自己的理解写, 没有照着对方的真东西写。** 隔离探测脚本在另一条线的分支上, 我先按它的说明文字写了一个判定替身, 5 处判定和真脚本不一样 (只是因为编排只看退出码是否非 0 才没有掩盖缺陷)。对方的文件是只读可看的。对策: 依赖别人的脚本时, 替身照它的源码写, 并留一条「真文件在就用真文件再跑一遍」的测试。
- **复用主仓的 venv 让测试进程摸到了主仓的数据。** 那个 venv 有一个指向主仓的可编辑安装, 全量 pytest 里在别的目录起的子进程因此打开了主仓的 chroma (只改了文件时间, 内容核对过完好)。是收尾前按提醒去核对才发现的。对策: 子工作区跑全量测试用自己的 venv; 「不写某个目录」这类约束, 收尾时用文件时间实际核对一遍, 不靠「我没有往那里写过」的印象。
- **「这次不换数据」我只想到了一种。** 协调方裁定「线上公开数据里有非 KB 集合、这次又不换数据时停站」, 我实现在指纹一致的那条路径上; 第四轮审查指出「公开数据落后且没有候选」那个提前返回的分支才是最常见的不换数据, 而检查排在它后面, 根本不跑。对策: 给一条断言找落点时, 先列出所有会提前返回的分支, 逐个问「走这条路时它还生效吗」。
- **真实运行一次都没有。** act_runner 对 job 级 `always()`、取消后的步骤、`concurrency` 的行为, 断网容器能否起到 healthy, `up --no-start` 的重建行为, 都只能等合并后的演练。未验证事项列了 8 条, 演练方案里给了逐条的只读核对命令。

## 关键决策复盘
1. **基线镜像: 差点选反。** 我先推理出「公开容器的镜像会无限期落后, 应改用私有线上镜像」, 理由听上去成立。动手前被指出要先看事实: 基线评测用的是镜像自带的题集和 KB, 判别条件是「镜像内 KB 指纹 == 数据的 stamp」; `git ls-tree` 一查, 很旧的那个镜像才与公开旧数据配对。最后保留设计原规则并把这个条件写成守卫。教训: 「哪个更合理」这类问题先找出可核对的判别条件, 再去核对, 不要先攒理由。
2. **kb-sync 没有照设计拆出独立的构建 / 清理 job。** 设计 v0.2 写的是独立 job 加跨 job 输出; 我改成每条腿自己 build (第二次命中缓存)、最后一条腿删。理由是这台 Gitea 上 job 级 `always()` 和 `needs.outputs` 从未真正跑过, 而私有腿是在用的生产流程, 不该让它依赖没验证过的机制。代价是两条腿有两步逐字重复, 用一条测试钉住。
3. **临时容器用「解析后的 compose 模型 + 白名单」生成, 而不是另写一份 compose 或整份照抄。** 另写一份会与对方会话改的 `compose.public.yml` 漂移; 整份照抄再删键会把将来新增的 ports / networks 带进来。白名单之外的键打印出来, 无法隔离的挂载直接拒绝。
4. **失败后一律停机, 不重启旧容器 (协调方代裁)。** 好处是失败路径上没有任何启动动作, 「不会意外拉起」可以用结构来保证; 代价是可恢复的小故障也会让公开站下线, 而且停着的容器可能是没通过的新镜像。后者做成了摘要里的明确提示, 没有再加「把镜像改回去」的动作 (那是另一条会失败的路径)。
5. **答题 key 只做免费的有效性探测。** 额度够不够验不了, 写进了未验证事项, 没有为了「看起来验过」加一次真答题。「不花钱」本身也只是从「该接口不产生 token 用量」推出来的, 官方文档没有计费条目, 这一点原样交给协调方判断。
6. **中途并进来的另一条线的要求 (网络预检 / 隔离核对 / 镜像下限)。** 这三样依赖的文件都在对方的分支上。做法是: 路径和网段从 compose 的解析结果里读, 不在这边写第二份; 对方的脚本按命令行接口调用, 文件不存在就失败 (两条线没一起合并时公开部署自然过不去, 而不是悄悄跳过检查); 对方给的 shell 写法原样照抄, 再加一条让真实 bash 执行它的测试。
8. **红线停站打印集合名的折中。** 裁定要求失败信息写明发现了哪些集合; 审查指出仓库里同类检查一向只打印计数, 而不按约定命名的集合名可能带真实研究的标识。最后的做法是约定的代号形态原样写、其余写指纹和长度, 并把这个出入明确告诉协调方, 而不是在「照原话做」和「照审查意见做」之间自己悄悄选一边。
9. **没有给私有 job 加 `shell: bash`。** 审查建议写死 shell 以防 runner 不是 bash。但显式指定 shell 可能多带一个 `pipefail`, 会改变这个 job 里几条管道的行为 —— 超出「只做加固」。保留现状, 把依据 (线上一直在跑 bash 才有的写法) 和这个取舍写进记录。
7. **编排自成进程组。** 这样中断兜底能把编排连同它起的 docker 子进程一起结束; 代价是如果 runner 靠给步骤的进程组发信号来取消, 编排会收不到。两种 runner 行为都没法在合并前确认, 选了「要么被兜底结束、要么按自己的状态机完整跑完」的那一边, 并把它列进未验证事项。
